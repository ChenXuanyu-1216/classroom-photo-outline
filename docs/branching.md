# 分支与合并约定

`main` 是当前可运行、状态说明可信的集成版本。分支名用于说明工作内容，不决定代码是否成熟，也不构成 Git 的合并权限。

## 三种不同的判断

| 层面 | 判断 | 处理 |
| --- | --- | --- |
| Git 提交关系 | 有无独有提交、是否出现冲突 | 已包含的提交不重复合并；冲突解决后重新验证 |
| GitHub 仓库设置 | 若启用分支保护，是否满足评审、状态检查和权限要求 | 满足实际配置，不绕过保护规则 |
| 本项目维护要求 | 是否适合主线、验证是否充分、文档是否准确 | 可用功能和状态清楚的资料可合入；破坏默认流程的未完成实验继续隔离 |

Git 可以合并不代表内容应当进入 main。反过来，存在冲突也不表示永远不能合并。技术规则见 [Git merge](https://git-scm.com/docs/git-merge)，仓库保护能力见 [GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。本文件没有宣称仓库已经启用某项保护设置。

## 本仓库的合入条件

1. 内容符合项目方向，变更范围明确，没有用较旧实现覆盖现有行为。
2. 功能代码通过相关测试；主线整合后运行完整工程检查。文档、数据变更核对路径、契约、文件哈希及状态说明。
3. 冲突已经解决，合并结果仍可运行；测试不通过时先查明原因，不为了清理分支强行合入。
4. 公开内容处于已确认的使用范围内，不包含密钥、本地私密路径或权限聊天全文。
5. 草稿、实验和已验收内容如实标注。资料进入 main 不代表模型质量、人工金标准或课程验收已经通过。

例如：可再分发的合成样例与空白模板可进入 main，但应准确标注合成、待复核和未运行状态。真实课堂照片及私人评价资料不属于默认源码贡献范围。如果是会破坏默认上传流程的识别实验，即使没有 Git 冲突，也应继续留在功能分支。

## 日常流程

从最新 main 创建 `codex/<英文修改内容>`，完成修改、验证和说明后整合。多人协作或需要审阅时使用 Pull Request；无论采用哪种路径，都遵守仓库实际配置的保护要求。合并决定以维护者授权为准。

合并完成后，确认每个待清理分支头都已包含在 main，且远端没有新增独有提交，再删除本地和远端分支引用。删除引用不删除 main 中保留的提交。未完成实验、有独有提交或仍被其他工作使用的分支保留；不强制删除、不强推覆盖远端。

当前发布准备与验证入口见[源码发布状态](open-source-release.md)。
